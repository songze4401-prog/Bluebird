This is an Expo / React Native mobile application (Expo SDK 57) with a local Express backend in `server/`. Prioritize mobile-first patterns, performance, and cross-platform compatibility.

## Expo has changed — do not trust your training data

Expo ships breaking changes every SDK release. APIs you remember are likely renamed, moved, or removed. Before writing any code that touches an Expo, EAS, or React Native API:

1. Read the major version of the `expo` package in `package.json`.
2. Fetch the matching versioned docs: `https://docs.expo.dev/versions/v<major>.0.0/`
3. For anything else, fetch https://docs.expo.dev/llms.txt — an index of all Expo docs with corrections to common LLM misconceptions. Follow its links to the specific page you need; never answer from memory.

## Architecture & navigation

- Single-screen app built from root `App.tsx`. **There is no Expo Router and no `src/app/` directory — do not add routes, route files, or navigation libraries.**
- Entry chain: `index.ts` (`registerRootComponent` + `SafeAreaProvider`) → root `App.tsx`, which renders the entire chat UI.
- Screen-like views are React Native `Modal` overlays opened from `App.tsx`: `components/MemoryScreen.tsx` (memory library), `components/ThemeScreen.tsx` (accent-color picker), and `components/HistoryScreen.tsx` (session list). Each is self-contained: it fetches its own data when `visible` flips to `true` and exposes only `visible` / `onClose` / `theme` (plus callbacks) to the parent.
- Multi-session wiring (frontend): `App.tsx` holds `currentSessionId` and sends it with every chat request (`/chat`, `/history`, `/history/clear`, `/history/recall`). On boot it reads `GET /sessions` (server returns `updatedAt`-desc order) and resumes the most recently updated session, falling back to `default` if the list is unavailable. The home screen's "new chat" creates a session eagerly via `POST /sessions`; "history" opens `HistoryScreen`. Session ids are not persisted on the client — the server list is authoritative.
- `components/` — UI components; each keeps its styles at the bottom of the file as `const createStyles = (theme: Theme) => StyleSheet.create({ ... })`.
- `theme.ts` — the theme system: mode (light/dark) × accent color. All light/dark color values are derived from the theme; components never hard-code them.
- `lib/` — shared non-UI code: `types.ts` (`Message`), `constants.ts` (API token, mood emoji, timing constants), `utils.ts` (helpers).
- `server/` — Express API, entry `server/index.js`, listens on port 3000 (`PORT`). Routes: `/chat` (DeepSeek via the `openai` SDK), `/sessions` (list/create), `/sessions/:id`, `/history`, `/history/clear`, `/history/recall`, `/memory`, `/memory/clear`, `/memory/delete`, `/emotion`; all except `/` require `Authorization: Bearer <token>` and pass through a rate-limit middleware. `server/sessions.js` owns multi-session storage and legacy migration, `server/memory.js` and `server/emotion.js` hold the domain logic; JSON state lives in `server/data/`.
  - Multi-session: `/chat`, `/history`, `/history/clear`, `/history/recall` all accept an optional `sessionId` (body for POST, query for GET). When omitted they fall back to the built-in `default` session, so clients that send no `sessionId` keep the legacy single-history behaviour. Unknown session ids are rejected with 404. `/chat` builds the model context from the session's stored messages; the client-supplied `history` is used as a fallback only for the `default` session (legacy clients) and only when that session is empty — a freshly created session never borrows another conversation's history. On first boot the legacy `server/data/chat-history.json` is imported into the `default` session, backed up in place, and never modified or deleted.
  - `/chat` persists before responding and returns `persisted` (`true`/`false`); a broken store therefore surfaces as `persisted: false` instead of a silent success. Persistence is synchronous, which also makes the same-session read-modify-write atomic (no `await` inside). Clients that disconnect before the reply is ready are not persisted, to avoid ghost messages.
  - Storage safety: `server/data/sessions.json` is the authoritative store. If it exists but cannot be read/parsed, or parses to an unexpected shape, the server enters read-only protection — it refuses all writes, leaves the file untouched at its original path (no rename, no delete), and serves a read-only fallback view built from the legacy history. Repairs must be done by hand on that file. This supersedes the older "rename to `.corrupt-<ts>`" behaviour **for `sessions.json` only** — that file is never renamed, and duplicate `.pre-multisession.bak-*` backups are not stacked. It must not be read as "the other modules changed too": `server/memory.js` and `server/emotion.js` still rename an unreadable file to `<file>.corrupt-<ts>` and continue with empty state (each is reported by its own corruption event — see "Data corruption events" below). `sessions.json` writes go through an `fsync` before the atomic rename (see "Atomic writes (C2)" below); orphan `messages` keys with no matching session are reported on load rather than dropped silently.
  - Memory attribution (E2 + contribution list): an entry stores its provenance as a **contribution list** — `contributions: [{ sessionId, sourceQuote, createdAt }]` — instead of a flat `sourceQuote` + `sessionId`. Every session that states the fact appends its own contribution; entry `createdAt` stays the earliest one, so it remains the `/memory/delete` key. Legacy entries that carry a flat `sourceQuote` are upgraded to a single contribution on load (`normalizeEntry`), and the flat fields disappear from the file on the next write. `/history/recall` matches **contributions**, not whole entries: it drops the contributions matching the recalled message's text (equality, containment, or ≥0.7 similarity) inside a `[messageTime − 5s, +2h]` window measured against *that contribution's* `createdAt`, preferring the current session's contributions and falling back to un-attributed (`sessionId: null`) legacy ones only when the current session has no match. Contributions from other sessions are never dropped, and an entry is deleted only once its last contribution is gone — so restating a fact in another session no longer reassigns (drifts) its attribution or replaces the original `sourceQuote` anchor, and recalling in session A still works after B restated the same fact. `recallMemoryBySourceQuote` returns the number of **entries** removed (a partial drop returns 0). `/memory` still serves a display-only `sourceQuote` (the earliest contribution's quote, derived in `getMemories`) so `components/MemoryScreen.tsx` needs no change. Dedupe/merge and `buildMemoryContext` retrieval stay global, and same-session + same-quote contributions are deduped (single-persona product).
  - Emotion decay (E3): `applyTimeDecay()` takes no arguments and is driven by a global `lastDecayAt` baseline (legacy state falls back to `updatedAt`), not by the current session's `gapSeconds`. The baseline advances on every check **and is persisted with that check** — not only when decay actually fires — so a single interval decays at most once, and switching into a long-idle session never re-applies that session's gap to the global emotion. Persisting unconditionally matters: if the baseline only advanced in memory, a restart during a no-decay gap would read the stale disk baseline and decay the same interval earlier than a run without the restart (measured: mid-run restart turns a no-decay 9-minute gap into a 12-minute one, `sad 60 -> 47`). Regression test in `tests/emotion-decay-global.test.js`.
  - Data corruption events (observability): the three modules keep **different** handling strategies on purpose (the dispatcher in `server/corruption.js` unifies only the entry point, not the strategies), and every corruption path emits one line of JSON to **stderr** via `server/data-events.js` (`logDataFileEvent`), so a headless / CI / Codespaces run can still locate the problem. Fields: `ts` (ISO timestamp), `level`, `event` (`data_file_corruption`), `module` (`sessions` | `memory` | `emotion`), `file` (absolute data-file path), `reason` (a controlled code: `json_parse_error` | `read_error` | `file_missing` | `io_error` | `invalid_shape`), `errorName` / `errorCode` (e.g. `SyntaxError`, `EACCES`), `action`, and `isolatedPath` only when a file was moved aside. `action` is what distinguishes the strategies: `read_only_protection` (`sessions.json` left in place, writes refused), `isolated_file` (`memory.json` / `emotion-state.json` renamed to `<file>.corrupt-<ts>`, empty state used), `isolation_failed` (the rename itself failed — the corrupted file stays put and empty state is still used). The event deliberately **never** records `error.message`: Node 20+ `JSON.parse` embeds a snippet of the offending input in its message, and that input is user chat text / memory content — only `error.name` / `error.code` are written, so logs never leak chat content, memory text, or secrets. `sessions.js` prints its human-readable banner in addition to the JSON line; all three still write to `stderr` (no new logging dependency). The same helper (`logDataEvent`) also records anomalies that are not "corruption" but still must be locatable, with the same record shape: `event=orphan_messages_detected` (level `warn`, `extra.count`) when `messages` keys have no matching session, `event=store_write_failed` / `event=write_queue_error` when persistence fails (action `write_failed`), `event=data_dir_error` when the data directory cannot be created, and `event=data_file_corruption` with action `legacy_import_skipped` for a corrupt `chat-history.json` (the legacy parse failure used to log `error.message`, which leaked chat text — it now records only `errorName` / `errorCode`).
  - Corruption handling contract (`server/corruption.js`): every corruption path goes through one dispatcher, `handleCorruption(moduleName, data, context)`. Each module registers one handler with `registerCorruptionHandler(name, handler)`; the handler implements `detect(data)` → `{ corrupt, reason?, error?, parsed? }` and `recover(context)` → `{ action, isolatedPath? }`, where `data` is `{ text, error }` (the raw file text just read, or the read error). `detect` only judges — it never mutates state — and returns the parsed value as `parsed` when healthy; on corruption the dispatcher calls `recover` with `reason` / `error` injected and then writes the single structured event itself, so callers no longer log corruption on their own. Registered handlers and their (deliberately different) strategies: `sessions` → in-place read-only protection (`action: read_only_protection`); `sessions.legacy` for `chat-history.json` → skip migration (`action: legacy_import_skipped`, logged with `module: sessions`); `memory` / `emotion` → rename aside to `<file>.corrupt-<ts>` (`action: isolated_file`, or `isolation_failed` when the rename fails). `handleCorruption` throws for an unregistered module, and `registerCorruptionHandler` throws a `TypeError` when the handler lacks `detect` or `recover`. Per-module `detect` differences are intentional and must be preserved: `sessions` also treats a JSON value that is not store-shaped as corruption (`invalid_shape`), whereas `emotion` does **not** — `normalizeState` tolerates any shape and falls back to `calm`, so only a read / parse failure counts there.
- Atomic writes (C2, resolved): all three modules now persist atomically with `fsync`. `server/atomic-write.js` exports `writeFileAtomicSync` / `writeFileAtomic`: write a temp file `<target>.tmp-<pid>-<ts>-<rand>` opened `'wx'` (same directory as the target, so the `rename` is atomic) → `fsync` it → close → `rename` it over the target → best-effort `fsync` of the parent directory; on any failure it closes the fd, unlinks the temp file, and rethrows. `server/memory.js` / `server/emotion.js` use it for every write (`memory.json`, `emotion-state.json`), and `server/sessions.js` keeps its own pid-suffixed temp file (`.tmp.<pid>`) with the same fd `fsync` before its atomic rename. A crash or power loss therefore never leaves an empty or truncated data file — the target always holds the full old or full new content. This supersedes the earlier C2 note that framed the memory / emotion difference as a known limitation.

  - **This is now enforced at startup by `server/single-instance.js`.** Before `app.listen`, the server atomically creates `<DATA_DIR>/.bluebird.lock` via `openSync(path, 'wx')` and records `{ pid, port, startedAt, dataDir }` in it. If the lock exists: the occupant's pid/port/start time are printed and the process exits with code 1 and the message `检测到另一个 Bluebird 实例正在使用该数据目录`. A stale lock is only cleaned up and taken over when the recorded pid is *provably* gone (`process.kill(pid, 0)` → `ESRCH`); if the pid's state can't be determined (e.g. `EPERM`), startup is refused rather than auto-taken-over. The lock is released on `exit`, and `SIGINT`/`SIGTERM` close the HTTP server first, then release it.
  - Escape hatch: `BLUEBIRD_ALLOW_MULTI=1` skips acquiring the lock (a warning is printed). Use it only when you accept the data-overwrite risk — e.g. short-lived probes, or when each instance actually gets its own `BLUEBIRD_DATA_DIR`. It never deletes another instance's lock file.
  - Manual recovery: confirm no Bluebird instance is running, then delete `<DATA_DIR>/.bluebird.lock` by hand and start again. (`DATA_DIR` is `BLUEBIRD_DATA_DIR` when set, otherwise `server/data`.)

## Commands

Use npm (`package-lock.json` is the only lockfile) — do not switch package managers or add bun/yarn/pnpm lockfiles.

```bash
npm install                  # install dependencies
npx expo install <package>   # ALWAYS use for Expo/RN packages — resolves SDK-compatible versions
npx expo start               # start the Metro dev server (:8081)
node server/index.js         # start the backend API (:3000)
npx tsc --noEmit             # typecheck
npx expo lint                # lint
npx expo-doctor              # diagnose dependency and config issues
```

In the Codespaces devcontainer, `bash scripts/blue-start.sh` (alias `blue`) idempotently starts both the API (:3000) and Metro (:8081).

Run lint and typecheck before declaring any task done.

### Tests

Twelve files, 305 checks total. Every `tests/*.test.js` file points `BLUEBIRD_DATA_DIR` at an OS temp directory (override supported by `sessions.js`, `memory.js`, and `emotion.js`), so tests never read or write the real `server/data`. Set `BLUEBIRD_DATA_DIR` **before** requiring any `server/` module — the data path is resolved once at module load, so setting it afterwards silently falls back to the real directory. Because `server/index.js` acquires the start-up single-instance lock before listening, tests that `require` it get a lock — but it lands in their own temp directory, so separate temp dirs never block each other. Run each file separately:

```bash
node --test --test-concurrency=1 tests/memory.test.js tests/emotion.test.js   # node:test suites (70)
node tests/api.test.js                    # 22 — HTTP/auth/rate-limit, custom runner
node tests/atomic-write.test.js           # 16 — temp+fsync+rename atomic writes, incl. a SIGKILL crash simulation
node tests/chat-persist.test.js           # 23
node tests/corruption-contract.test.js    # 26 — detect/recover contract + all three modules routed through handleCorruption
node tests/data-events.test.js            # 34 — corruption + anomaly event logging & protection behaviour
node tests/emotion-decay-global.test.js   # 10 — global baseline decay incl. restart-safety
node tests/memory-session-scope.test.js   # 19 — contribution list, attribution, recall scope
node tests/session-scope-e2e.test.js      # 19 — live HTTP end-to-end for E2/E3
node tests/sessions-recovery.test.js      # 36
node tests/sessions.test.js               # 30
```

- The two `node:test` suites declare `{ concurrency: 1 }` on every `describe`: suites within a file share one data file, and the corruption-recovery case renames it to `.corrupt`. The other ten are minimal custom-runner scripts (not `node:test`) that exit explicitly.
- `tests/data-events.test.js` covers the corruption events end to end: it corrupts each of the three data files in its own temp directory and asserts the structured stderr line has every field (`ts` / `module` / `file` / `reason` / `action`) and that the original protection behaviour is unchanged (`sessions.json` left byte-identical with writes refused, `memory.json` / `emotion-state.json` renamed aside). It also seeds a sentinel string into each corrupt file and asserts it never appears in the log, guarding the "no chat / memory content in logs" rule. The `isolation_failed` case is forced with `Object.defineProperty(fs, 'renameSync', …)` — a plain assignment does not work because Node's `fs` exports some functions as lazy getters. It also covers the non-corruption anomalies: a corrupt `chat-history.json` (`legacy_import_skipped`, asserting the file's chat text never reaches the log), orphan `messages` keys (`orphan_messages_detected`, keeping the old human warning), a refused `sessions.json` write (`store_write_failed`), and failed memory / emotion writes (`write_queue_error`, with `fs.promises.rename` forced to fail the same way).
- `tests/atomic-write.test.js` proves the atomic write helper: `writeFileAtomicSync` / `writeFileAtomic` create, overwrite, and keep the target intact when the `rename` fails (old content preserved, temp file cleaned up). Its crash case spawns a child process that writes the old value, makes `fs.promises.rename` kill itself with `SIGKILL` **before** the rename, then writes the new value — after the child dies, the parent asserts the target still holds a complete, parseable old (or new) value and is never empty or truncated, and that any leftover temp file matches the `.tmp-<pid>-<ts>-<rand>` naming.
- `tests/corruption-contract.test.js` guards the unified contract: section 1 unit-tests the dispatcher (registration rejects a handler missing `detect` / `recover`, an unregistered module throws, healthy data skips `recover` and logs nothing, corrupt data calls `recover` with the reason / error injected and logs exactly one event); section 2 replaces `handleCorruption` with a recording spy **before** requiring the modules (they destructure it, so the spy wins) and asserts each module reaches it — `sessions`, `sessions.legacy` (corrupt `chat-history.json`), `memory`, `emotion` — while each strategy still behaves as documented; section 3 asserts `emotion` still does not treat a wrong shape as corruption; section 4 asserts healthy files never trigger recovery. The spy wraps the real implementation so the event assertions still hold.
- `tests/api.test.js` is a legacy reference script rather than a `node:test` suite: it drives the live HTTP endpoint on a fixed port (`3999`) and keep the `PORT`/`BLUEBIRD_API_TOKEN` env setup at the top.
- To disable the LLM in a test, assign `process.env.DEEPSEEK_API_KEY = ''` — do **not** `delete` it. `dotenv` only fills keys that are absent, so a deleted key is re-injected from `server/.env` when `server/index.js` loads, which sends real requests and incurs real cost.
- Never read or write `server/data/` from a test. It holds the real memory, chat history, and emotion state; `.gitignore` excludes it, so anything a test wipes there cannot be recovered.
- Verify isolation by seeding `server/data/` with sentinel content, running the full suite, and checking the files are byte-identical afterwards.

## Rules

- If `ios/` and `android/` directories do not exist, they are generated (Continuous Native Generation). Never create or edit them by hand — configure native behavior in `app.json` and config plugins.
- Expo Go only includes its bundled native modules. After adding a library with native code, the app needs a development build: `npx expo run:ios|android` locally, or `eas build --profile development`.
- Prefer recommended Expo modules over third-party libraries; add them with `npx expo install`. Docs: https://docs.expo.dev/versions/latest/index.md
- Local persistence uses `@react-native-async-storage/async-storage` — do not introduce other storage dependencies.
- `.env` files hold secrets (API keys, tokens) and are configured per machine — never edit or overwrite them as part of code changes.
