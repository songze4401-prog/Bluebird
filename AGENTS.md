This is an Expo / React Native mobile application (Expo SDK 58) with a local Express backend in `server/`. Prioritize mobile-first patterns, performance, and cross-platform compatibility.

## Expo has changed — do not trust your training data

Expo ships breaking changes every SDK release. APIs you remember are likely renamed, moved, or removed. Before writing any code that touches an Expo, EAS, or React Native API:

1. Read the major version of the `expo` package in `package.json`.
2. Fetch the matching versioned docs: `https://docs.expo.dev/versions/v<major>.0.0/`
3. For anything else, fetch https://docs.expo.dev/llms.txt — an index of all Expo docs with corrections to common LLM misconceptions. Follow its links to the specific page you need; never answer from memory.

## Architecture & navigation

- Single-entry app built from root `App.tsx` with a `home` / `chat` view switch. **There is no Expo Router and no `src/app/` directory — do not add routes, route files, or navigation libraries.**
- Entry chain: `index.ts` (`registerRootComponent` + `SafeAreaProvider`) → root `App.tsx`, which renders the entire chat UI.
- Screen-like views are React Native `Modal` overlays opened from `App.tsx`: `components/MemoryScreen.tsx` (memory library), `components/ThemeScreen.tsx` (accent-color picker), `components/HistoryScreen.tsx` (session list), `components/ControlPanelScreen.tsx` (persona), `components/ModelScreen.tsx` (providers). `MemoryScreen` / `ControlPanelScreen` / `ModelScreen` fetch their own data when `visible` flips to `true` (they are the only consumers of that data, so a hook would only add indirection). `HistoryScreen` is **controlled** since the state-layering pass: it receives `sessions` / `loadingSessions` / `sessionsError` / `onRefresh` from `App.tsx` and never calls `/sessions` itself — there is exactly one list source (`hooks/useSessionList.ts`).
- Chat shell: `components/BottomTabBar.tsx` switches the chat/tasks view, `components/SettingsDrawer.tsx` hosts history/memory/persona/models/theme/clear, and `components/TasksPanel.tsx` is an explicit empty state because the backend has no task API yet. Do not present it as a working task feature.
- Frontend state ownership (state-layering pass — **`App.tsx` is composition + routing only, ~300 lines; do not put chat logic back into it**):
  - `hooks/useChatSession.ts` — owns `messages` / `loadingHistory` / `loadingOlder` / `sending` / `continuing` / `mood` and the whole send / continue / load-history / load-older / clear / recall orchestration. Send and "continue" share one internal `runChat` runner; the only differences (error bubble vs. Alert) are callbacks. Both paths snapshot `sessionId` at request entry and both are mutually exclusive (a send is refused while a continuation is in flight and vice versa).
  - `hooks/useSessionList.ts` — the single `/sessions` source (list + `loading` + `error` + `refresh`).
  - `hooks/useSessionActions.ts` — create / select / delete session (`POST /sessions`, `DELETE /sessions/:id`), plus the shared `busy` guard.
  - `hooks/useModelSelection.ts` — the only `/model-providers` consumer for the default model; refreshed by `ModelScreen`'s `onDefaultsChanged` callback (the old "re-read on modal close" is gone).
  - `hooks/useThemePreference.ts` / `useStreamingPreference.ts` / `useAttachments.ts` — local preferences and the pick-image → upload → pending-attachment flow.
  - `lib/chat-messages.ts` — pure `Message[]` transforms (segment normalisation, streaming bubble replacement, mood / `modelNote`, history mapping, welcome message).
  - Session ids are not persisted on the client — the server list is authoritative. Every `/chat` and `/chat/stream` call sends the model snapshot taken at request entry as `providerId` + `modelId`, so switching the model after sending never changes an in-flight request; a failed read simply omits the pair (server global default applies).
  - Race protection: `lib/api/latest-request.ts` (`createRequestGate`) is used by history loading and session-list refresh — `begin()` aborts the previous in-flight request and issues a token, `isCurrent(id)` discards stale responses even if the abort did not land. History loads that were superseded return `{ stale: true }` and callers must not change the session or raise an error for them.

- Network layer (`lib/api/`): `client.ts` (`apiFetch` + `TIMEOUTS`) is the **only** place that calls `fetch` — an ESLint `no-restricted-syntax` rule forbids `fetch(...)` in `App.tsx` and `components/**` (severity `error` since the fetch-guard phase). `apiFetch` always attaches `Authorization`, adds `Content-Type` when there is a body, applies a per-request timeout (default 15 s; `TIMEOUTS.chat` / `upload` 60 s, `presence` 10 s) and merges a caller-supplied `AbortSignal`. `endpoints.ts` is the only place that builds paths; `errors.ts` defines `ApiError` (`status` / `code` / `detail` / `requireConfirm` + `actionHint` for `auth` / `not_configured` / `capability` / `rate_limit` / `endpoint_missing`); `types.ts` holds the per-endpoint request/response contracts (verified against `server/index.js`, not guessed). SSE lives in `lib/stream.ts` (XHR, 60 s) because RN fetch cannot read a streaming body; its `StreamEvent` is a discriminated union of the six server event types (`meta` / `delta` / `done` / `error` / `tool_start` / `tool_end`).
- Module-system boundary (`lib/text-rules.ts`): `split-reply.js`, `sticker-markers.js` and `streaming-segments.js` stay **CommonJS** because the same implementations are required by `server/index.js` (plain `node`, no build step), by `node:test` files, and by Metro. Their types come from sibling `*.d.ts` files, and **`lib/text-rules.ts` is the only frontend module allowed to import them** — anything else importing those paths breaks the boundary. Converting them to TS/ESM would force a build step on the server and the tests; if that ever happens, it must be done in `text-rules.ts` + deleting the three `.js` files, not by adding a second path.
- `components/` — UI components; each keeps its styles at the bottom of the file as `const createStyles = (theme: Theme) => StyleSheet.create({ ... })`.
- `theme.ts` — the theme system: mode (light/dark) × accent color. All light/dark color values are derived from the theme; components never hard-code them.
- `lib/` — shared non-UI code: `types.ts` (`Message`, `ReplyMode`, session/model/persona types), `constants.ts` (API token, mood emoji, timing constants), `utils.ts` (helpers), `chat-messages.ts` (message transforms), `text-rules.ts` (the CJS text-rule seam), `api/` (network layer), `stream.ts` (SSE), `uploads.ts` (image upload / sticker repo), `presence.ts` (presence reporting). `hooks/` holds the React state layer.
- `server/` — Express API, entry `server/index.js`, listens on port 3000 (`PORT`). Routes: `/chat` (model calls via `server/model-adapter.js`), `/chat/stream` (SSE variant), `/sessions` (list/create), `/sessions/:id`, `/history`, `/history/clear`, `/history/recall`, `/memory`, `/memory/clear`, `/memory/delete`, `/emotion`, `/presence`, `/presence/report`, `/model-providers` (+ `/:id`, `/default`, `/:id/enabled`, `/:id/test` — multi-provider management); all except `/` require `Authorization: Bearer <token>` and pass through a rate-limit middleware. `server/sessions.js` owns multi-session storage and legacy migration, `server/memory.js` and `server/emotion.js` hold the domain logic; JSON state lives in `server/data/`.
  - Multi-provider model layer (`server/api-configs.js` + `server/model-adapter.js`): provider configuration is decoupled from call logic. The built-in DeepSeek provider is derived from `DEEPSEEK_API_KEY` at runtime (never persisted, cannot be edited or deleted) and remains the default provider/model — an existing deployment upgrades with zero reconfiguration. Custom providers are OpenAI-Chat-Completions-compatible (`baseUrl` + `apiKey` + model list, each model declaring only the capabilities the code actually relies on — `vision`; unknown capabilities are never faked). Metadata lives in `api-configs.json`, API keys in a **separate** `api-keys.json` (chmod 0600 best-effort, plaintext at rest — see the data table below); no route ever returns a full key (`keyConfigured` + masked `keyHint` only), and `PATCH` with an absent/empty `apiKey` keeps the existing key. `model-adapter.js` owns the network surface: client cache per provider, unified stream/non-stream calls, error normalisation (`auth`/`rate_limit`/`timeout`/`connection`/`server`/`model`/`bad_request` → fixed HTTP mapping, messages scrubbed of the key), connection testing (`GET {baseUrl}/models`, 5 s timeout, 64 KB response cap), and SSRF defence — user-supplied `baseUrl` values are DNS-resolved and rejected when they point at loopback/private/link-local (incl. cloud metadata `169.254.169.254`) addresses, with credentials or non-http(s) schemes. `BLUEBIRD_ALLOW_PRIVATE_BASE_URL=1` is a **test-only** bypass (loud startup warning; never set it in production). Vision requests: with images attached, a model that declares `vision` handles them directly; a non-vision model triggers same-provider vision routing (the preferred default vision model, otherwise the first enabled vision model) and the response reports it — never a silent downgrade. The `/chat` and `/chat/stream` `done` payloads therefore carry `modelRoute: { requested: { providerId, providerName, modelId, source: 'request' | 'default' }, actual: { providerId, providerName, modelId }, auto, reason: 'vision_unsupported' | null }`. `model` is the model this system actually sent; `upstreamModel` is only the supplier's echoed name (several suppliers rewrite it — DeepSeek echoes `deepseek-flash` for a `deepseek-chat` request), so it must never be used to prove routing. A provider with no vision model fails with `code: capability` instead of pretending the text model saw the image. Chat requests may also carry request-level `providerId` + `modelId`: they are resolved for that request only and never written back to the global default; when omitted, the stored global default in `api-configs.json` → `defaults` is used (older clients). Unknown/disabled provider, unknown model, or missing key fail with a structured error and never fall back to another model. Memory extraction and sticker semantics keep using the built-in DeepSeek client (`getMemoryClient`), unchanged from before.
  - Agent tool calling V1 (`server/agent-runtime.js` + `server/tool-memory-search.js` + `server/tool-memory-remember.js` + `server/text-utils.js`): a bounded tool loop (3 rounds max, `BLUEBIRD_AGENT_MAX_ROUNDS` clamped 2–5) that runs only when **all three gates** pass — `BLUEBIRD_AGENT_TOOLS=1` (read per request, default off), the target model declares `capabilities.tools === true` (`supportsTools`; unknown ⇒ false), and the request carries no **new image** (`hasNewImage`; history images do not disable Agent and are sent only when the target model supports vision). A new image with a non-vision model is routed to a vision model, and Agent is disabled with the user-visible `agentNotice`; `[agent-gate]` logs `reason` as `newImage`, `noToolsCapability`, `switchOff` or `allowed`. Any failed gate falls through to the original one-shot path unchanged. Registered tools are `memory_search` (read-only), `knowledge_search` (read-only unified retrieval across memory/conversation/document/web/code; sessionId is injected by the runtime, never accepted from model arguments) and `memory_remember` (candidate writes through the same decision/lifecycle pipeline as automatic extraction; user-quote grounding, sensitive-content and session ownership are enforced server-side). There is **no weather or general network tool** in this repository: when asked for live weather, the model must say the capability is unavailable rather than inventing data. A future tool must be added as a separate registered module with its own parameter schema, timeout, permission boundary, unit test and end-to-end test; do not pre-build a weather abstraction now. Tool rounds are non-stream; the final text still goes through the same mood-tag stripper → `delta` → `done` path, and the stream gains two additive event types (`tool_start` / `tool_end`) that older clients ignore. Execution summaries (`{ name, ok, summary, durationMs }` — no arguments, no memory text, no model reasoning) are persisted as a separate `toolSteps` field on the last assistant message and echoed in `/chat`, the stream `done` payload and `/history`; they are never concatenated into `content`. A client disconnect aborts in-flight tool work via `AbortController`.
  - Memory retrieval engine (`server/memory.js` `searchMemories` + `buildMemoryContext`, `server/memory-semantic.js`, exposed through `memory_search`): candidates are filtered **before** scoring and truncation. Session scope is mandatory and reused from `scopeOf`; optional filters cover source type (`user`/`agent`/`tool`/`model`/`import`), status (`active`/`superseded`/`archived`; `pending` is never a retrievable fact) and a time range over `valid` / `created` / `updated`. Dimensions combine with AND, arrays with OR, and an entry missing a requested field is **not** a match. Ranking combines keyword hits (0.7) and character-bigram overlap (0.3) into lexical relevance, then blends it with concept-level semantic relevance at 0.7 / 0.3. The semantic layer is a local dictionary of 17 concrete concepts (coffee/editor/city/cat/name/nickname/job/allergy/theme/project/birthday/exam/computer/spicy_food/travel/license_plate/dietary_restriction) that handles synonym, hypernym and Chinese–English concept matches; it is **not** a neural embedding and is marked `semanticKind: 'concept_lexicon_v1'`, `neural: false`, `limited: true`. There is no local embedding runtime or model cache in this repository, so open-domain/vector semantic recall remains an explicit blocker — see `docs/memory-semantic.md` and the fixed evaluation in `docs/memory-semantic-eval.md`; do not describe the concept dictionary as vector semantics. The composite score multiplies hybrid relevance by type weight (`identity` 1.15 / `preference` 1.1 / `goal` 1.05 / `relationship` 1 / `fact` 0.95), time decay (event-like `fact`/`goal` only, floor 0.85; stable identity/preference/relationship stay at 1), status weight (`active` 1 / `superseded` 0.45 / `archived` 0.3 / `pending` 0) and confidence weight. Budgets are enforced together: item count, per-item code points, total code points and an approximate token budget (`heuristic-cjk-ascii-v1`, not a tokenizer claim). Results carry `score`, `relevance`, `match.reason`/keywords plus `match.semantic` (concepts/coverage/precision/provider/limited), score components, `sourceTypes`, IDs, `contentTruncated`, and `diagnostics` with exclusion counts, truncation flags and `notReturned` reasons; the tool returns the compact model-facing fields plus budget/exclusion metadata. Small memory stores no longer bypass relevance filtering — `identity` entries are retained by an explicit type rule, not by a size threshold.
  - Agent tools switch: template default is `BLUEBIRD_AGENT_TOOLS=0` in `server/.env.example`; only the exact string `1` enables tools, and the value is read from `process.env` per request. Editing `server/.env` does **not** affect an already-running Node process — restart the backend after changing it. `scripts/blue-start.sh` never sets or overrides the user's value; it prints only `Agent tools: enabled|disabled` by loading `server/.env` in a throwaway Node process (never prints keys or the file). Enabling tools needs a tools-capable text model and no **new** images; history images are allowed when the target model supports both vision and tools. It increases model rounds, latency and cost. `server/.env` is not committed; `server/.env.example` is the only tracked template.
  - Context Runtime v3 (current, single chain): every `/chat` and `/chat/stream` request runs `runContextRuntime` (`server/context/engine.js`); the old `BLUEBIRD_CONTEXT_ENGINE` switch and the `softTarget`/`perTypeMax`/fixed-guarantee budget are gone. `projection.js` defines the stored-message contract (id/role/content/createdAt/attachments/toolSteps); `history.js` selects a token-bounded recent window (which can exceed 20 messages), recalls older relevant messages, and `summary.js` builds a traceable extractive summary; `retriever.js` is memory-only (`searchMemories`, session-scoped), `coverage.js` skips only sufficiently covered items and resolves memory-vs-newer-history conflicts, `input-guard.js` enforces the final model input limit with a deterministic degradation order and explicit 413, and `trace.js` records candidate/selected/accepted/injected/sent (`consumed` stays null because HTTP success is not consumption evidence). External document/web/code retrieval is provided by the separate unified retrieval service (next bullet), not by the old in-engine doc/web source stubs; memory retrieval remains `searchMemories`. Agent tool results are request-local and recorded per round in the sent trace. The built-in `deepseek-chat` has no provider-declared `contextWindow` (it is absent from `/models`), so the guard uses an explicitly labelled unknown-window guard; `deepseek-flash` declares the provider-reported 1,048,576-token window; real vision is gated by `npm run eval:context` on a fixed 256×256 pure-red PNG, with the criterion split in two: the request side is deterministic (every sample must return 200 and the trace must show `imageCount === 1`), while the model side is sampled **3 times and must be correct in a majority (≥2/3)** — the evidence line prints every raw answer plus `correct=n/3`, so a single lucky sample is never reported as stable. The model itself is genuinely non-deterministic: a smaller 64×64 image once answered white, and the same 256×256 bytes produced both 8/9 and 9/9 evaluation runs on different days — treat anything below 3/3 as model-side variance, not as a pipeline failure. `deepseek-flash` declares `input_modalities=[text,image]`.
  - Unified retrieval v1 (`server/retrieval/*`, `docs/unified-retrieval.md`): five source connectors (memory, conversation, document, web, code) share one chunk contract with a stable `chk_…` id derived from source/rule/content-hash/locator, an explicit visibility scope, and a derived index under `BLUEBIRD_DATA_DIR/retrieval/index.json`. The query path runs BM25 + exact (symbols/paths/error codes) + optional neural vector recall in parallel, fuses with RRF, dedupes, applies scope/status/validity/traceability/prompt-injection policy, then packs an evidence list with separate retrieval/authority/confidence/freshness signals and a query-hash-only trace. Memory and conversation chunks are strictly session-scoped; document/web/code are global in this single-user deployment. The index is derived and rebuildable; `POST /retrieval/ingest|sync|rebuild` and `DELETE /retrieval/sources/:id` require Bearer auth, while `POST /retrieval/search` never mutates business source data, but may idempotently refresh the derived memory/conversation index. `POST /retrieval/sync` re-reads document/code sources by hashed root + relative path and removes deleted files; web refresh requires the URL to be re-supplied because raw query parameters are not stored. Context Engine injects only document/web/code as a separate low-priority `knowledge` block; memory/history keep their existing paths. Embedding is an optional OpenAI-compatible provider (`BLUEBIRD_RETRIEVAL_EMBEDDING_*`); when it is absent the vector channel is explicitly unavailable and lexical/exact still work. PDF/DOCX parsing, a production neural embedding endpoint, reranking and query rewrite remain **not implemented / unverified** — do not describe them as done. PDF/DOCX is format coverage (safe rejection), reranker/query rewrite are quality optimizations, and full AST is a code-quality improvement; these are not all launch blockers. File ingest is restricted to `BLUEBIRD_RETRIEVAL_ROOTS`; web ingest rejects loopback/private/link-local/metadata targets and pins the validated DNS address into the connection lookup (no resolve-then-reconnect TOCTOU), with a test-only `BLUEBIRD_RETRIEVAL_ALLOW_PRIVATE_URL` bypass. Async ingest/sync/rebuild writes are serialized in-process; the store is atomic single-file and refuses writes after an isolation failure. document/web/code are global in this single-user deployment, while memory/conversation are session-scoped; traces/index writes never include query or chunk body text.
  - Agent Policy v1 (`server/agent-policy.js`, `docs/agent-policy.md`): a separate, versioned, server-owned policy (`agent-policy.json`) controls autonomy mode (`answer_only` / `plan_then_act` / `bounded_autonomy`), planning prompt hints, a tool allowlist, max tool calls, max total time, one read-only retry and max rounds. `/agent-policy` GET/PUT/reset require Bearer auth; the control panel reads and saves it. Defaults preserve existing Agent behavior. Enforcement is in `agent-runtime.js`: `answer_only` / empty allowlist are blocked at the gate, tools are filtered from the request, total time and tool-call budgets stop the loop with a `stopReason`, and tools declared `risk: 'high_risk'` are denied with `confirmation_required` until an approval protocol exists. The strict schema rejects unknown fields/out-of-range values; the file uses atomic writes and safe-default corruption isolation. Trace records policy digest/revision/gate/stopReason without content. There are no high-risk tools in the current registry and no parallel tool execution.
  - Agent write-tool safety (current): `memory_search` is `readOnly: true`; `memory_remember` is `readOnly: false`. The runtime rejects a write tool without `sessionId` + current `userText` before the handler; the handler additionally enforces source-quote grounding, sensitive-content filtering, session ownership and `targetId` scope through `applyCandidate`. A pre-aborted write returns without persisting. There is no weather/network/write-external tool in this repository.
  - Multi-session: `/chat`, `/history`, `/history/clear`, `/history/recall` all accept an optional `sessionId` (body for POST, query for GET). Each session retains up to 1000 messages (`SESSION_MESSAGE_MAX`); `/history` returns at most 200 per page (`HISTORY_PAGE_MAX`), accepts a `before` message-id cursor and returns `hasMore` / `nextCursor`, while the client loads older pages 50 at a time. When retention trims old messages, unreferenced upload files are released; `getMessages()` still returns the full retained window for model context and recall. When omitted they fall back to the built-in `default` session, so clients that send no `sessionId` keep the legacy single-history behaviour. Unknown session ids are rejected with 404. `/chat` builds the model context from the session's stored messages; the client-supplied `history` is used as a fallback only for the `default` session (legacy clients) and only when that session is empty — a freshly created session never borrows another conversation's history. On first boot the legacy `server/data/chat-history.json` is imported into the `default` session, backed up in place, and never modified or deleted.
  - `/chat` persists before responding and returns `persisted` (`true`/`false`); a broken store therefore surfaces as `persisted: false` instead of a silent success. Persistence is synchronous, which also makes the same-session read-modify-write atomic (no `await` inside). Clients that disconnect before the reply is ready are not persisted, to avoid ghost messages.
  - Storage safety: `server/data/sessions.json` is the authoritative store. If it exists but cannot be read/parsed, or parses to an unexpected shape, the server enters read-only protection — it refuses all writes, leaves the file untouched at its original path (no rename, no delete), and serves a read-only fallback view built from the legacy history. Repairs must be done by hand on that file. This supersedes the older "rename to `.corrupt-<ts>`" behaviour **for `sessions.json` only** — that file is never renamed, and duplicate `.pre-multisession.bak-*` backups are not stacked (one is still written by the legacy migration when none exists — see "Data safety & backup" below). It must not be read as "the other modules changed too": `server/memory.js` and `server/emotion.js` still rename an unreadable file to `<file>.corrupt-<ts>` and continue with empty state (each is reported by its own corruption event — see "Data corruption events" below). `sessions.json` writes go through an `fsync` before the atomic rename (see "Atomic writes (C2)" below); orphan `messages` keys with no matching session are reported on load rather than dropped silently.
  - Memory attribution (E2 + contribution list): an entry stores its provenance as a **contribution list** — `contributions: [{ sessionId, sourceQuote, createdAt }]` — instead of a flat `sourceQuote` + `sessionId`. Every session that states the fact appends its own contribution; entry `createdAt` stays the earliest one, so it remains the `/memory/delete` key. Legacy entries that carry a flat `sourceQuote` are upgraded to a single contribution on load (`normalizeEntry`), and the flat fields disappear from the file on the next write. `/history/recall` matches **contributions**, not whole entries: it drops the contributions matching the recalled message's text (equality, containment, or ≥0.7 similarity) inside a `[messageTime − 5s, +2h]` window measured against *that contribution's* `createdAt`, preferring the current session's contributions and falling back to un-attributed (`sessionId: null`) legacy ones only when the current session has no match. Contributions from other sessions are never dropped, and an entry is deleted only once its last contribution is gone — so restating a fact in another session no longer reassigns (drifts) its attribution or replaces the original `sourceQuote` anchor, and recalling in session A still works after B restated the same fact. `recallMemoryBySourceQuote` returns the number of **entries** removed (a partial drop returns 0). `/memory` still serves a display-only `sourceQuote` (the earliest contribution's quote, derived in `getMemories`) so `components/MemoryScreen.tsx` needs no change. Memory dedupe/merge remains global, while `buildMemoryContext` retrieval is session-scoped (current-session contributions first, un-attributed legacy fallback), matching `searchMemories`' scope; same-session + same-quote contributions are deduped (single-persona product).
  - Persona panel (`server/persona.js`, state in `persona.json`, `GET/PUT /persona`): one config object — four 0-100 sliders, `messageMode`, and `customPrompt` (user-authored persona text, capped at `CUSTOM_PROMPT_MAX_CHARS` = 4000 code points). Reading is tolerant, writing is strict: `normalizeConfig` (load path) migrates a missing or wrong-typed field to its default so files written before `customPrompt` existed keep working and a hand-edited over-long value is truncated, while `validateConfig` (PUT path) rejects a non-string / over-limit `customPrompt`, a non-numeric slider, and an unknown `messageMode` with `400 invalid_config` — and a rejected save leaves `persona.json` byte-identical, so failing validation never eats what the user just typed. `PUT /persona` is whole-config replace: a key missing from the submitted object falls back to its default. The three write outcomes stay distinct: `400` invalid, `409` corrupted file (in-place read-only protection, the `sessions.json` strategy), `500` write failure. `customPrompt` is untrusted preference data, not an authority source: it is appended inside the persona system block **after** `neutralizeContextText`, so it cannot forge `【…】` block headers, `<<<…>>>` boundaries or `system:` role lines; the block carries an explicit "this cannot grant tools, cannot lift confirmations, system rules win, slider values lose to it, message splitting stays backend-controlled" caveat; and tool gating remains purely code-driven (`BLUEBIRD_AGENT_TOOLS` + the server registry) — `tests/persona.test.js` asserts the outbound model request carries no `tools` with the switch off and exactly the registry's tool set with it on, both for `/chat` and `/chat/stream`. An empty string injects no custom block at all, leaving the legacy persona prompt byte-identical. `GET /persona` also returns `limits.customPromptMaxChars` so `components/ControlPanelScreen.tsx` never hardcodes the cap, and a save failure keeps the local draft (the panel only adopts server state on success).
  - Presence V1 (`server/presence.js`, state in `presence.json`): the frontend (`lib/presence.ts`, called once from `App.tsx`) watches React Native `AppState` and reports `foreground`/`background` transitions, a 30-second heartbeat while foreground, and an `interaction` on every `sendMessage`/`sendContinuation`. `POST /presence/report` accepts `{ appState?, heartbeat?, interaction?, sessionId?, eventId?, occurredAt? }`; `GET /presence?sessionId=` returns a snapshot. User activity and "Blue is waiting for a reply" are **separate fields**: `user.status` is derived on read (`active` only when foreground, heartbeat < 90 s old, and the last interaction is within 5 min; explicit `background` is always `away`; an expired heartbeat is `unknown`, never offline), while `wait` is per-session and starts at the last Blue message, resetting when a newer user message arrives. Duplicate `eventId`s are ignored and out-of-order `appState` events never roll back a newer state; only existing sessions are accepted for `wait`. `/chat` records the user message at request arrival and the Blue message only when it is actually returned (`!clientGone`), and `/history/clear`, `/history/recall`, `DELETE /sessions/:id` reset/remove the session's wait state. Presence writes are atomic and failure-isolated (never fail a chat request); `presence.json` is runtime observation data and is isolated as `.corrupt-<ts>` on parse failure.
  - Emotion decay (E3): `applyTimeDecay()` takes no arguments and is driven by a global `lastDecayAt` baseline (legacy state falls back to `updatedAt`), not by the current session's `gapSeconds`. The baseline advances on every check **and is persisted with that check** — not only when decay actually fires — so a single interval decays at most once, and switching into a long-idle session never re-applies that session's gap to the global emotion. Persisting unconditionally matters: if the baseline only advanced in memory, a restart during a no-decay gap would read the stale disk baseline and decay the same interval earlier than a run without the restart (measured: mid-run restart turns a no-decay 9-minute gap into a 12-minute one, `sad 60 -> 47`). Regression test in `tests/emotion-decay-global.test.js`.
  - Data corruption events (observability): the three modules keep **different** handling strategies on purpose (the dispatcher in `server/corruption.js` unifies only the entry point, not the strategies), and every corruption path emits one line of JSON to **stderr** via `server/data-events.js` (`logDataFileEvent`), so a headless / CI / Codespaces run can still locate the problem. Fields: `ts` (ISO timestamp), `level`, `event` (`data_file_corruption`), `module` (`sessions` | `memory` | `emotion`), `file` (absolute data-file path), `reason` (a controlled code: `json_parse_error` | `read_error` | `file_missing` | `io_error` | `invalid_shape`), `errorName` / `errorCode` (e.g. `SyntaxError`, `EACCES`), `action`, and `isolatedPath` only when a file was moved aside. `action` is what distinguishes the strategies: `read_only_protection` (`sessions.json` left in place, writes refused), `isolated_file` (`memory.json` / `emotion-state.json` renamed to `<file>.corrupt-<ts>`, empty state used), `isolation_failed` (the rename itself failed — the corrupted file stays put and empty state is still used). The event deliberately **never** records `error.message`: Node 20+ `JSON.parse` embeds a snippet of the offending input in its message, and that input is user chat text / memory content — only `error.name` / `error.code` are written, so logs never leak chat content, memory text, or secrets. `sessions.js` prints its human-readable banner in addition to the JSON line; all three still write to `stderr` (no new logging dependency). The same helper (`logDataEvent`) also records anomalies that are not "corruption" but still must be locatable, with the same record shape: `event=orphan_messages_detected` (level `warn`, `extra.count`) when `messages` keys have no matching session, `event=store_write_failed` / `event=write_queue_error` when persistence fails (action `write_failed`), `event=data_dir_error` when the data directory cannot be created, and `event=data_file_corruption` with action `legacy_import_skipped` for a corrupt `chat-history.json` (the legacy parse failure used to log `error.message`, which leaked chat text — it now records only `errorName` / `errorCode`).
  - Corruption handling contract (`server/corruption.js`): every corruption path goes through one dispatcher, `handleCorruption(moduleName, data, context)`. Each module registers one handler with `registerCorruptionHandler(name, handler)`; the handler implements `detect(data)` → `{ corrupt, reason?, error?, parsed? }` and `recover(context)` → `{ action, isolatedPath? }`, where `data` is `{ text, error }` (the raw file text just read, or the read error). `detect` only judges — it never mutates state — and returns the parsed value as `parsed` when healthy; on corruption the dispatcher calls `recover` with `reason` / `error` injected and then writes the single structured event itself, so callers no longer log corruption on their own. Registered handlers and their (deliberately different) strategies: `sessions` → in-place read-only protection (`action: read_only_protection`); `sessions.legacy` for `chat-history.json` → skip migration (`action: legacy_import_skipped`, logged with `module: sessions`); `memory` / `emotion` / `presence` → rename aside to `<file>.corrupt-<ts>` (`action: isolated_file`, or `isolation_failed` when the rename fails). `handleCorruption` throws for an unregistered module, and `registerCorruptionHandler` throws a `TypeError` when the handler lacks `detect` or `recover`. Per-module `detect` differences are intentional and must be preserved: `sessions` also treats a JSON value that is not store-shaped as corruption (`invalid_shape`), whereas `emotion` does **not** — `normalizeState` tolerates any shape and falls back to `calm`, so only a read / parse failure counts there.
- Atomic writes (C2, resolved): all three modules now persist atomically with `fsync`. `server/atomic-write.js` exports `writeFileAtomicSync` / `writeFileAtomic`: write a temp file `<target>.tmp-<pid>-<ts>-<rand>` opened `'wx'` (same directory as the target, so the `rename` is atomic) → `fsync` it → close → `rename` it over the target → best-effort `fsync` of the parent directory (tries `'r+'` first — the only flag Windows accepts for a directory handle, so the earlier `'r'`-only attempt silently did nothing on Windows — then falls back to `'r'` for POSIX, where `'r+'` fails with `EISDIR`); on any failure it closes the fd, unlinks the temp file, and rethrows. `server/memory.js` / `server/emotion.js` / `server/presence.js` use it for every write (`memory.json`, `emotion-state.json`, `presence.json`), and `server/sessions.js` keeps its own pid-suffixed temp file (`.tmp.<pid>`) with the same fd `fsync` before its atomic rename. A crash or power loss therefore never leaves an empty or truncated data file — the target always holds the full old or full new content. This supersedes the earlier C2 note that framed the memory / emotion difference as a known limitation.
- Change record (this phase): added `server/atomic-write.js` (fsync atomic writes) and `server/corruption.js` (detect/recover contract + `handleCorruption`); routed `server/sessions.js` (`sessions` + `sessions.legacy`), `server/memory.js`, and `server/emotion.js` through the contract and switched their writes to atomic writes; added `tests/atomic-write.test.js` (incl. a `SIGKILL` crash simulation) and `tests/corruption-contract.test.js`; resolved C2.
- Deployment constraint (A3): `server/data/` is loaded once into a per-process in-memory cache and rewritten in full, so **the API must run as a single process**. Do not run multiple instances against the same data directory (or behind a load balancer without sticky routing) — concurrent instances overwrite each other's state silently (measured: two instances writing 15 unique memories each kept 28/30 sequentially and 14/30 concurrently, with the loser crashing on `EPERM ... memory.json.tmp`).
  - **This is now enforced at startup by `server/single-instance.js`.** Before `app.listen`, the server atomically creates `<DATA_DIR>/.bluebird.lock` via `openSync(path, 'wx')` and records `{ pid, port, startedAt, dataDir }` in it. If the lock exists: the occupant's pid/port/start time are printed and the process exits with code 1 and the message `检测到另一个 Bluebird 实例正在使用该数据目录`. A stale lock is only cleaned up and taken over when the recorded pid is *provably* gone (`process.kill(pid, 0)` → `ESRCH`); if the pid's state can't be determined (e.g. `EPERM`), startup is refused rather than auto-taken-over. The lock is released on `exit`, and `SIGINT`/`SIGTERM` close the HTTP server first, then release it.
  - Escape hatch: `BLUEBIRD_ALLOW_MULTI=1` skips acquiring the lock (a warning is printed). Use it only when you accept the data-overwrite risk — e.g. short-lived probes, or when each instance actually gets its own `BLUEBIRD_DATA_DIR`. It never deletes another instance's lock file.
  - Manual recovery: confirm no Bluebird instance is running, then delete `<DATA_DIR>/.bluebird.lock` by hand and start again. (`DATA_DIR` is `BLUEBIRD_DATA_DIR` when set, otherwise `server/data`.)
  - Temporary write files carry the pid: `sessions.json.tmp.<pid>` (`sessions.js`) and `memory.json.tmp-<pid>-<ts>-<rand>` / `emotion-state.json.tmp-<pid>-<ts>-<rand>` (`server/atomic-write.js`). Tests that occupy a tmp path to simulate write failures must reproduce that exact naming. Regression guards: `tests/memory.test.js` and `tests/emotion.test.js` hook `fs.promises.open` / `fs.promises.rename` (the async FileHandle path `writeFileAtomic` uses) and fail unless the tmp file's own `sync()` is observed before the rename — the post-rename directory fsync cannot satisfy the assertion.
- Config: the frontend reads `EXPO_PUBLIC_API_URL` and `EXPO_PUBLIC_BLUEBIRD_API_TOKEN` from the root `.env` (Expo only exposes `EXPO_PUBLIC_*` variables); the backend reads `server/.env` (`DEEPSEEK_API_KEY`, `BLUEBIRD_API_TOKEN`, `PORT`, `MEMORY_ENABLED`, plus optional `BLUEBIRD_RETRIEVAL_*` settings documented in `server/.env.example`). See both `.env.example` templates; the client and server tokens must match.

## Data safety & backup

Everything the user owns lives in one directory: `server/data/`, or `BLUEBIRD_DATA_DIR` when set. `.gitignore` excludes it, so **user data is never in git** — a fresh clone starts with zero data, and nothing in the repo restores it. There is no automatic backup; `scripts/blue-backup.sh` / `scripts/blue-backup.ps1` are the tool for that.

| File in the data directory | Role |
| --- | --- |
| `sessions.json` | **Authoritative store** — every session and message; subsumes the legacy history after migration. |
| `memory.json` | Long-term memory entries (contribution list, E2). |
| `emotion-state.json` | Emotion state incl. the global decay baseline (E3). |
| `presence.json` | Presence V1 runtime observation: `lastSeenAt`, `lastInteractionAt`, last Blue message time, app state, per-session user/Blue message times, recent event ids for dedupe. Disposable; never affects chat, memory, or emotion. |
| `chat-history.json` | **Legacy, frozen** — read exactly once by the first-boot migration (`importLegacyHistory`); no code path writes it, so multi-session-era messages never land here. |
| `chat-history.json.pre-multisession.bak` | The pre-migration copy of `chat-history.json`, written once when absent (see the storage-safety note above). It is the only snapshot taken *before* session rewriting started. |
| `<file>.corrupt-<ts>` | A `memory.json` / `emotion-state.json` that could not be read was renamed aside and the service continued with empty state (`sessions.json` never does this — read-only protection instead). No code reads these files and nothing prunes them; the only signal is a server-log line, which a headless run hides. Inspect, then delete by hand. |
| `<file>.bak-<ts>` | Output of the older rename-based mechanism; no longer produced, and no current code reads, updates, or cleans existing ones. |
| `.bluebird.lock` | The single-instance lock (A3). Normal while a server runs; a stale one is handled under "Manual recovery" above. It is runtime state, not data — backups skip it. |
| `uploads/` | Multimodal image store: uploaded chat images (`kind=image`) and the sticker library (`kind=sticker`, index in `uploads/stickers.json`). Messages reference files by UUID; orphaned files are deleted only after a whole-store reference check (`getAllMessages`), and `DELETE /uploads/image/:id` refuses with 409 while any message still references it. |
| `api-configs.json` | Multi-provider configuration (providers, models, capability declarations, defaults) — **contains no API keys**. Corrupt → in-place read-only protection (writes refused, file untouched), same strategy as `sessions.json`. |
| `api-keys.json` | API keys for custom providers, stored separately from the metadata above (chmod 0600 best-effort; **plaintext at rest**, protected by file permissions + the `server/data` gitignore only — no static encryption, since a hardcoded master key is forbidden; a KMS / passphrase-derived scheme is a documented follow-up). Never returned by any route, never logged. Corrupt → renamed aside to `.corrupt-<ts>`, providers fall back to "key not configured". |
| `sticker-repo/` | Sticker repository files (`sticker-repo/files/<uuid>.<ext>`) with the index in `sticker-repo.json`; physical delete removes both file and index entry. |

### Backup

There is exactly **one** implementation: `server/backup.js` (logic) driven by `scripts/bluebird-backup.js` (CLI). `scripts/blue-backup.sh` / `scripts/blue-backup.ps1` are thin wrappers that forward to it — do not reimplement the flow in a shell script.

**Why the wrappers exist:** the pre-2026-10 shell/PowerShell versions copied only *top-level files* (`for src in "$DATA_DIR"/*` filtered by `-f`), so `uploads/` (chat images) and `sticker-repo/` (sticker library) were skipped **silently** — the run printed `✓ 备份完成` while a restore would lose every image and the whole sticker library. The Node implementation walks the tree recursively; that gap is the reason both old entry points now delegate instead of staying independent.

```bash
node scripts/bluebird-backup.js                     # -> $HOME/bluebird-backups/data-<ts>/
node scripts/bluebird-backup.js --out-dir /mnt/usb  # another disk = a different failure domain
node scripts/bluebird-backup.js --keep 14
node scripts/bluebird-backup.js --check             # status only; exit 2 when stale or last run failed
node scripts/bluebird-restore-drill.js              # isolated restore rehearsal (see below)

bash scripts/blue-backup.sh /mnt/usb                # wrapper, positional arg = backup root
pwsh scripts/blue-backup.ps1 -OutDir 'E:\backups'   # wrapper (ASCII-only on purpose, see below)
```

What a run guarantees:

- **Scope** — recursive over the whole data directory, dotfiles included; runtime artifacts (`.bluebird.lock`, `*.tmp.*` / `*.tmp-*`) are skipped and reported, because restoring a lock makes the server refuse to start, believing another instance is alive. `.corrupt-<ts>` / `.bak-<ts>` files *are* included (forensic value, tiny).
- **Secrets are excluded by default** — `api-keys.json` (the plaintext key store) is **never** placed in a snapshot. It is recorded under `skippedSecrets` in the manifest and the run prints `未备份（密钥，默认排除）`. If a deployment genuinely needs the keys backed up, pass `--encrypt-secrets` together with `BLUEBIRD_BACKUP_KEY` (a high-entropy passphrase, stored in a secret manager — never committed); the key is then written as `<name>.enc` (AES-256-GCM) and the plaintext never appears in the snapshot. `restoreSnapshot` decrypts it back only when `BLUEBIRD_BACKUP_KEY` is present at restore time (`restore_missing_key` otherwise).
- **Integrity** — every file must be non-empty, parse as JSON (with a shape rule for the store-critical ones: `sessions.sessions` must be an **array** and `sessions.messages` an **object**), and match its copy's SHA-256. `MANIFEST.json` records `path / bytes / sha256 / structure` per file.
- **Consistency** — each module persists via temp file + `fsync` + atomic rename, so a single file is always self-consistent; there is no cross-file transaction. The run therefore re-stats every source file after copying and retries once if any changed, and **fails** (`source_changed_during_copy`) rather than shipping a possibly-skewed snapshot.
- **Traceable run log** — `<backup root>/_state/runs.jsonl` gets one appended JSON line per run: `ts`, `ok`, `snapshotDir`, `durationMs`, `files`, `bytes`, `manifestSha256`, `error`. `<backup root>/_state/last-status.json` holds `lastRunOk`, `lastSuccessAt`, `lastSuccessSnapshot`, `consecutiveFailures`, `lastError`, `disasterRecoveryGrade`.
- **Staleness is detectable, not assumed** — `--check` exits `0` when healthy, `2` when there is no status file, no successful run, the last success is older than `--stale-hours` (default 24), or the last run failed, and `1` on a check error. Exit `0` means "the status is healthy", **not** "a scheduler is running".
- **Retention** — `--keep N` (default 7) prunes only snapshots this tool wrote (`data-*` containing `MANIFEST.json` with a matching `formatVersion`). Legacy `MANIFEST.txt`-only directories are never deleted.
- **Failure domain / disaster recovery is NOT claimed by a local path** — a backup root inside the data directory is refused (`out_root_inside_data`). When the root sits on a different drive letter it records `differentLogicalDrive: true` but still sets `disasterRecoveryGrade: false` with `offHostUnverified: true`: a different drive letter on the **same physical disk** (e.g. this host's C: and D: are both `KINGSTON SA400S37240G`, Disk0) is only logical separation and survives neither a dead disk nor a dead machine. True DR requires the root to be on a **different machine or remote storage**; the tool cannot confirm that from a local path, so it never asserts it.

**Alerting watchdog.** `scripts/bluebird-backup-check-alert.js` wraps `--check`: on a non-zero exit it appends one JSON line to `<backup root>/_state/alerts.jsonl` and, if `BLUEBIRD_ALERT_CMD` is set, executes that command (the alert JSON is passed via the `BLUEBIRD_ALERT_PAYLOAD` env var; it does not touch stdout logs). A scheduler should call the watchdog (not the bare backup) so failures surface. The watchdog preserves the check's exit code, so the scheduler's own failure notification also fires.

**Scheduling is not configured by this repo.** Nothing in the repository installs a cron job, systemd timer, or Windows scheduled task, and the tests do not simulate one. The deployment must wire it explicitly, for example on Windows:

```bat
:: 每日 03:07 备份（指向异机/远端时才是真正 DR；本机 C:/D: 同盘仅逻辑隔离）
schtasks /Create /TN "BluebirdBackup" /SC DAILY /ST 03:07 /TR "cmd /c node <repo>\scripts\bluebird-backup.js --out-dir <independent-or-remote-root> --keep 7"

:: 每日 03:37 检查健康度，异常则写 alerts.jsonl 并可外发
schtasks /Create /TN "BluebirdBackupWatchdog" /SC DAILY /ST 03:37 /TR "cmd /c set BLUEBIRD_ALERT_CMD=<your-notifier> && node <repo>\scripts\bluebird-backup-check-alert.js --out-dir <independent-or-remote-root>"
```

On Linux/macOS the equivalent is a crontab line (`0 3 * * * cd <repo> && node scripts/bluebird-backup.js --keep 7`, plus a `--check` probe). A manual run is **not** evidence that scheduled backups work, and a local `--out-dir` is **not** evidence of disaster recovery.

`scripts/blue-backup.ps1` is intentionally **ASCII-only** so it no longer depends on the UTF-8 BOM (PowerShell 5 decodes a BOM-less file with the system ANSI codepage). If you ever re-add non-ASCII text to it, the BOM becomes mandatory again. `scripts/blue-backup.sh` must not have a BOM (it breaks the shebang).

### Restore

1. **Rehearse first.** `node scripts/bluebird-restore-drill.js` restores the latest snapshot into an isolated `mkdtemp` directory, re-verifies every hash and structure, loads the restored data through the real `server/` modules (`sessions.listSessions`, `sessions.getAllMessages`, `memory.getMemories`, `emotion.getEmotion`, `persona.getConfig`), cross-checks the counts the modules report against the counts in the files, and proves the production directory's tree digest is unchanged. It never writes to the production data directory, never starts the server, and never calls a model. Records land in `<backup root>/_state/drills.jsonl`.
2. Stop the server and confirm no instance holds `<DATA_DIR>/.bluebird.lock`.
3. Replace the contents of `<DATA_DIR>` with the backup directory's contents — keep the old directory aside instead of deleting it.
4. Start the server: the JSON is loaded as-is, and sessions, memories, and emotion come back exactly as they were at backup time.

A drill note: `sessions.js` enforces "the default session always exists", so a restored store that lacks it gets one created on first load. The drill tolerates `sessions >= file count` for that reason and treats a *shortfall* as the failure signal.

Reviving the **legacy** history out of `chat-history.json.pre-multisession.bak` is a separate manual path, because that file is a `chat-history.json` and not a `sessions.json`:

1. Stop the server.
2. Move `sessions.json` aside. The migration runs only when the store cannot be loaded at all (`importLegacyHistory` is called on `!loadedFromDisk`), so any readable `sessions.json` suppresses it.
3. Put the `.bak` back in place as `chat-history.json`.
4. Start the server: the migration re-creates the `default` session from that file and writes a fresh `sessions.json`. Sessions that lived in the moved-aside store are **not** merged back — recover them by hand if you need both.

The thirty-seven direct-runner entries consist of twenty-nine custom-`check()` scripts plus eight `node:test` files invoked one file at a time; exit codes are authoritative, and there is no single TAP aggregate across all thirty-seven (each `node:test` file emits its own `ℹ tests/pass/fail`). `context-engine-e2e.test.js` proves the context runtime is always-on (setting `BLUEBIRD_CONTEXT_ENGINE=0` changes nothing), flips `BLUEBIRD_AGENT_TOOLS` per group, and exits at the end (no cross-file state).
- `tests/data-events.test.js` covers the corruption events end to end: it corrupts each of the three data files in its own temp directory and asserts the structured stderr line has every field (`ts` / `module` / `file` / `reason` / `action`) and that the original protection behaviour is unchanged (`sessions.json` left byte-identical with writes refused, `memory.json` / `emotion-state.json` renamed aside). It also seeds a sentinel string into each corrupt file and asserts it never appears in the log, guarding the "no chat / memory content in logs" rule. The `isolation_failed` case is forced with `Object.defineProperty(fs, 'renameSync', …)` — a plain assignment does not work because Node's `fs` exports some functions as lazy getters. It also covers the non-corruption anomalies: a corrupt `chat-history.json` (`legacy_import_skipped`, asserting the file's chat text never reaches the log), orphan `messages` keys (`orphan_messages_detected`, keeping the old human warning), a refused `sessions.json` write (`store_write_failed`), and failed memory / emotion writes (`write_queue_error`, with `fs.promises.rename` forced to fail the same way).
- `tests/atomic-write.test.js` proves the atomic write helper: `writeFileAtomicSync` / `writeFileAtomic` create, overwrite, and keep the target intact when the `rename` fails (old content preserved, temp file cleaned up). Its crash case spawns a child process that writes the old value, makes `fs.promises.rename` kill itself with `SIGKILL` **before** the rename, then writes the new value — after the child dies, the parent asserts the target still holds a complete, parseable old (or new) value and is never empty or truncated, and that any leftover temp file matches the `.tmp-<pid>-<ts>-<rand>` naming.
- `tests/corruption-contract.test.js` guards the unified contract: section 1 unit-tests the dispatcher (registration rejects a handler missing `detect` / `recover`, an unregistered module throws, healthy data skips `recover` and logs nothing, corrupt data calls `recover` with the reason / error injected and logs exactly one event); section 2 replaces `handleCorruption` with a recording spy **before** requiring the modules (they destructure it, so the spy wins) and asserts each module reaches it — `sessions`, `sessions.legacy` (corrupt `chat-history.json`), `memory`, `emotion` — while each strategy still behaves as documented; section 3 asserts `emotion` still does not treat a wrong shape as corruption; section 4 asserts healthy files never trigger recovery. The spy wraps the real implementation so the event assertions still hold.
- `tests/api.test.js` is a legacy reference script rather than a `node:test` suite: it drives the live HTTP endpoint on an OS-assigned port (`PORT=0`, read back from `server.address().port` once `listening` fires), so a busy fixed port can never silently redirect its destructive assertions (`/memory/clear`, `/history/clear`) at another instance. Keep the `PORT`/`BLUEBIRD_API_TOKEN` env setup at the top. It also carries two isolation tripwires of its own: a pre-flight `isolationError()` that validates the *effective* `BLUEBIRD_DATA_DIR` value before any destructive request, and a post-run md5 diff of the real `server/data/` that turns silent pollution into a failed check.
- To disable the LLM in a test, assign `process.env.DEEPSEEK_API_KEY = ''` — do **not** `delete` it. `dotenv` only fills keys that are absent, so a deleted key is re-injected from `server/.env` when `server/index.js` loads, which sends real requests and incurs real cost.
- Never read or write `server/data/` from a test. It holds the real memory, chat history, and emotion state; `.gitignore` excludes it, so anything a test wipes there cannot be recovered.
- Monitoring is on by default in production but **off for generic tests**: `scripts/run-tests.js` and `scripts/verify-test-coverage.js` set `BLUEBIRD_MONITORING=0`. Monitoring-specific files set it back to `1` before loading modules and use their own `BLUEBIRD_DATA_DIR`. Monitoring data lives in `<data>/monitoring/` and is metadata-only.
- Verify isolation by seeding `server/data/` with sentinel content, running the full suite, and checking the files are byte-identical afterwards.
- **Coverage gate:** `node scripts/verify-test-coverage.js` re-runs every backend file and Jest, and compares per-file runtime counts with `scripts/test-coverage-baseline.json`. It also parses `.github/workflows/ci.yml` (explicit `tests/*.test.js` paths and `for f in …` runner lists, comments stripped) and fails if a registered test file is not covered by a CI runner, or if CI names a file that is not in the baseline. Adding, removing, or re-counting a test file requires updating that baseline, the workflow lists, `AGENTS.md`, and the CI comment in the same change. Static `check(`/`test(` call-site scanning is deliberately not used as the source of truth: `memory-startup-lock` executes three checks per each of three loop iterations (+6 over call sites), and `delete-semantics` calls its upload helper five times (+4 over one call site), which explains the 204 static vs 214 runtime total for the 11 new files.
- **Two runners, two directories — do not mix them.** `tests/*.test.js` are `node:test` / custom-runner files driven by `npm test` (`scripts/run-tests.js`, non-recursive) and CI. `tests/unit/**/*.test.ts(x)` are **jest** files (`npm run test:unit`, preset `jest-expo`), used for anything that needs TypeScript or React. `package.json` → `jest.testMatch` is pinned to `tests/unit/**` on purpose: without it jest would try to load the `node:test` files and fail. The reverse is also true — do not put a `.test.js` file under `tests/` that assumes jest globals.

## Rules

- If `ios/` and `android/` directories do not exist, they are generated (Continuous Native Generation). Never create or edit them by hand — configure native behavior in `app.json` and config plugins.
- Expo Go only includes its bundled native modules. After adding a library with native code, the app needs a development build: `npx expo run:ios|android` locally, or `eas build --profile development`.
- Prefer recommended Expo modules over third-party libraries; add them with `npx expo install`. Docs: https://docs.expo.dev/versions/latest/index.md
- Local persistence uses `@react-native-async-storage/async-storage` — do not introduce other storage dependencies.
- Monitoring (`server/monitoring/`) is read-only from the client: never add cleanup/config/tool-execution endpoints under `/monitoring`; all routes must reuse `requireAuth` and keep query limits. Event/trace payloads must stay metadata-only (no prompts, memory text, tool args/results, keys). See `docs/observability.md`.
- `.env` files hold secrets (API keys, tokens) and are configured per machine — never edit or overwrite them as part of code changes.
