一句话结论：主控聊天、Context、记忆、检索、Agent 工具和审批主流程是真实可运行的；但 Memory Bot 的“会话身份”被错误地当成“记忆 scope”，导致委派 Bot 读不到父会话记忆、写入也落在错误作用域。这是 P0，且现有测试没有覆盖。

最关键的 5 个问题

P0存在缺陷
委派 Memory Bot 使用独立 Bot 会话，读不到父主控会话的记忆，写入也落在错误作用域
delegate_to_bot 为每个任务新建 bs_ 会话，runtime 把该会话作为工具 sessionId；memory scope 只允许本会话贡献或 legacy，导致主控会话的 session-scoped 记忆对 Bot 不可见。Bot 的 memory_remember 也把贡献写到 bs_ 会话，主控之后看不到。
P1存在缺陷
备份包含 Bot Vault 主密钥与加密凭证，AES-256-GCM 的静态加密被备份抵消
backup 只排除 api-keys.json；agent-vault.key 与 agent-credentials.json 会一起进入快照。拿到备份的人可同时获得主密钥和密文。损坏的 api-keys.json.corrupt-* 也不匹配排除名。
P1存在缺陷
Bot 凭证没有在运行时绑定到当前 provider，切换模型后可能把旧 Key 发给新服务商
config.updateConfig 可改 providerId/modelId 而保留 credentialId；getCredentialKey 只校验 botId，不校验 record.providerId；registry 只检查存在凭证；调用时 keyOverride 直接用于新 provider。
P1存在缺陷
审批驱动的任务完成绕过实时 Result Delivery，父会话要等到重启或 SSE 重连才看到结果
approvals.execute 直接把关联 task 置为 completed/failed 并写结果，但没有调用 resultDelivery.deliverTaskOutcome；投递只在启动恢复或 SSE snapshot 时发生。
P1存在缺陷
切换会话期间仍可发送，消息进入旧会话并从新会话视图消失
selectSession 先 await loadHistory 再 setCurrentSessionId；loadHistory 未把 loadingHistory 置 true；发送守卫只看 sending/continuing/loadingHistory。加载 B 历史期间发送会写入 A，随后 B 历史覆盖视图。

边界与单点

核心单点

  • sessions.json 单文件 + 进程内 sync 写
  • agent-tasks.json/agent-events.json 单文件与单进程队列
  • result-delivery 使用进程内 EventEmitter，无跨进程投递
  • memory.json 单文件 + enqueueWrite 单进程串行
  • retrieval/index.json 单文件 + 最多 64MB 向量
  • 模型服务商是唯一外部依赖；Provider 不可用时仅词法/精确降级

断裂/缺口

  • 统一 retrieval 有 backend API，没有前端 UI
  • memory.maintain/memory.audit 是 accepted task type，但没有维护/审计工具
  • 任务取消 API 没有任务页按钮
  • 审批完成不走实时 result delivery
  • session delete 不清理 uploads/retrieval conversation index
  • 删除记忆/撤回不立即清理 retrieval derived index
