## 32. R3 审批与资源期限：两套独立约束

### 32.1 两套独立约束

【条款正文（v1.3 生效）】

1. **审批期限**：R3 不设自动批准超时，Approval Request 可长期 `pending`；任何人不得以“等待过久”为由自动批准或超时放行。
2. **资源期限**：Task `deadline`、Task Token 预算、Run 总预算在 `waiting_approval` 期间照常有效；等待墙钟时间计入 Run 时间预算。
3. **任一硬约束耗尽**：立即停止执行。无未核清副作用 → `timed_out`；副作用结果未知或未核清 → 先 `recovery`（沿用 §24.1）。
4. 资源耗尽不转化为批准，等待过久也不转化为批准。

【条款正文（v1.3 生效）】用户裁决原话：

> 审批可以无限期等待，但不能让任务无限期占用资源。

**关闭项：** 上一轮缺口 #5 前半段（§24.2 `waiting_approval → timed_out` 与 §29 R3「不设超时」的冲突）。

### 32.2 修订 §24.2 的 `waiting_approval` 迁移行

【条款正文（v1.3 生效）】

| 当前状态 | 允许的下一状态 | 触发主体 / 条件 |
| --- | --- | --- |
| `waiting_approval` | `running`、`cancelled`、`failed`、`timed_out`、`recovery` | 有效批准→`running`；拒绝/取消/审批流程失败→`failed`/`cancelled`；资源期限耗尽且无未核清副作用→`timed_out`；资源期限耗尽但副作用未知→`recovery` |

`timed_out` 在此表示**因资源期限终止**，与审批期限无关；不改变 Approval Request 的 `pending` 状态，也不产生批准效果。

**关闭项：** 上一轮缺口 #5；与 §24.1 对齐。

### 32.3 `overdue` 标记与升级动作

【条款正文（v1.3 生效）】

- `overdue` 是 Approval Request 上的标记，不是 Task 状态，不进入 §24.1 状态集合。
- 升级动作：生成 escalation 事件 → 进入有明确责任人的审批队列 → 通知责任人 → 按轮值继续升级 → 保持 `overdue` 直至处理；不得静默遗忘，也不得把长期未处理变成批准。
- 审批系统故障 fail-closed；通知失败不视为审批完成（沿用 §29）。

【建议，待用户确认】`escalationAt` 由 Task `deadline` 派生（例如 50%），可按风险等级单独配置；比例经实测校准并留痕。

【建议，待用户确认】Task 已 `timed_out` 后，对应 Approval Request 可保留 `pending`/`overdue` 供人工处置与审计，但不得再触发执行；人工后续批准必须新建 task / 新 run 并引用原记录（§24.2 终态纠错），不给已终止任务“复活”通道。

### 32.4 与 §25 预算的关系

【条款正文（v1.3 生效）】

- 等待审批不产生模型调用 Token，但持续占用 Task 执行槽位并消耗 Run `deadline` 时间预算。
- 资源判定使用服务端原子计量（§25），不接受 Worker 或审批端自报数值。
- 批准后剩余预算不足以完成执行时，不得以“已获批准”为由超预算；应返回 `budget_exceeded` 或请求人工追加预算。

## 33. R0/R1 fail-open 显式策略表

### 33.1 默认规则：未命中即 fail-closed

【条款正文（v1.3 生效）】

1. 未命中白名单的动作一律 fail-closed，不因“低风险惯例”“历史曾批准”放行。
2. 白名单只适用于 R0/R1；R2 永不 fail-open（§29）；R3 永不 fail-open（只接受显式授权批准）。
3. fail-open 只跳过人工审批等待，不跳过确定性验证、证据校验、`trustLevel` 规则（§13、§27）、预算与权限校验（§16）。
4. 命中判定必须全字段匹配：动作、参数摘要、主体、适用环境、计划/产物版本、有效期；任一不匹配即 fail-closed。
5. 审批系统故障、策略版本不可读时 fail-closed（沿用 §29）。

【建议，待用户确认】审计记录写入失败同样 fail-closed，不得先执行后补审计。

### 33.2 策略表的 7 个必需字段

【条款正文（v1.3 生效）】缺任一字段则该条策略无效：

| # | 字段 | 定义与约束 |
| --- | --- | --- |
| 1 | 动作范围 | 允许的工具/动作类型、参数模式、目标资源范围；必须枚举或白名单，禁止通配符与“同类动作”推定 |
| 2 | 预授权主体 | 有权预授权的角色或人员清单；Agent、Orchestrator、Gateway 不得作为预授权主体（§2.6） |
| 3 | 风险等级 | 仅 R0/R1；出现 R2/R3 即整条策略失效，不得降级匹配 |
| 4 | 有效期 | 绝对起止时间 + 次数上限 + 单次/长期类型；过期或用尽立即失效，不自动续期 |
| 5 | 适用环境 | 环境标识（dev/staging/prod）与资源标识；不匹配不得放行，禁止跨环境继承 |
| 6 | 审计记录 | 必填：`policyId`、`policyVersion`、`matchedRule`、动作、参数摘要、主体、`taskId`、`runId`、决策、时间、`traceId`、预授权人引用 |
| 7 | 撤销机制 | 撤销主体、生效时机（立即或下一请求生效）、传播方式、撤销审计；撤销后未完成请求不得继续 |

【建议，待用户确认】落库键名：`actionScope`、`preAuthorizedSubjects`、`riskLevel`、`validity`、`environmentScope`、`auditRecord`、`revocation`。

### 33.3 策略变更与复核

【条款正文（v1.3 生效）】

- 策略表属于 §2.6 禁止 Agent 自行修改的“审批规则”，只能人工按版本化流程变更。
- 每次变更记录：策略版本、变更内容、批准人、生效时间、回滚点。
- 每条 fail-open 审计记录绑定当次 `policyVersion`。
- 撤销权独立于策略编辑权。

【建议，待用户确认】复核周期：每季度，或风险评估、环境、预授权主体变化时立即复核。

## 36. 数值参数分类表

### 36.1 两条封版硬约束

【条款正文（v1.3 生效）】

- **A 类**：可先给安全默认值，标注“可先定，待实测校准”；允许作为安全兜底进入运行，但不得作为容量、性能或成本承诺。
- **B 类**：必须压测或基线测量才定，标注“待压测，未压测前不得作为生产标准”；不得写入对外 SLA、容量规划或成本承诺。

## 37. 来源优先级与冲突裁决规则

### 37.1 有序来源等级

【条款正文（v1.3 生效）】定义 `sourceAuthority` 有序枚举，高等级压过低等级：

| 等级 | 来源类别 | 示例 | 依据 |
| --- | --- | --- | --- |
| L0 | 法规、合同、用户显式指令 | 合规要求、用户当次明确约束 | §12（新增，L0–L5 命名已采纳） |
| L1 | 系统权威数据源、签名/校验通过的凭证 | 权威系统返回值、签名回执 | §12、§28 |
| L2 | 一手原始材料 | 原始日志、原始文件、官方文档原文 | §12、§2.5 |
| L3 | 已验证的内部产物 | `evidence_checked`、`independently_verified` 的 Artifact | §12、§27 |
| L4 | 仅声明、未验证的内部产物 | `declared`、Producer 自述 | §27 |
| L5 | 外部网页、第三方二手内容、模型生成摘要 | 抓取页面、转述、摘要 | §12、§16 |

规则：

- 未知来源默认 L5，并打污点标签（§16）。
- 等级只表示来源权威，不表示内容正确；L1 与 L2 冲突仍需走裁决。
- 数量不构成权重：多个 L4 不能压一个 L3，多 Agent 投票不能代替证据（§2.5）。
- `trustLevel` 与 `sourceAuthority` 是正交维度，不能互相替代（§27）。

### 37.2 同级裁决与升级

【条款正文（v1.3 生效）】同级冲突按以下顺序裁决，前项能唯一确定即停止：

1. 版本覆盖：明确声明取代且 `supersedes` 关系可验证的新版本优先（§10、§11）。
2. 签名/校验结果：校验通过优先于未校验（§12）。
3. 时间有效性：在有效期内且更新者优先；过期一律降级（§12、§14）。
4. 业务约束：满足验收条件与业务规则者优先（§12）。
5. schema 与完整性：结构完整、必需字段齐全者优先（§2.5、§12）。

仍无法唯一确定：

- 由独立 Reviewer 提建议并记录理由（§12、§28）。
- 高风险、影响外部副作用或政策冲突 → 有权限的人类最终裁决（§12、§13）。
- 未解决冲突只能作为 `provisional` 使用，不得解锁高风险工具（§12）。
- 禁止伪造 `selectedCandidateRef`；裁决结果写为新 Artifact 版本或独立决策记录，不覆盖原始候选（§28）。

【建议，待用户确认】同级内若“时间更新”与“签名有效”同时指向不同候选，按“签名优先于时间”处理，理由是可验证性强于新鲜度。

【条款正文（v1.3 生效）】用户 2026-11-03 授权采纳：`sourceAuthority` 字段名与 L0–L5 枚举名写入 `ConflictRecord` 与 Artifact 元数据，作为 `policyVersion` 的一部分冻结。

## 38. `orphan` TTL、清理策略与审计例外

### 38.1 默认 TTL 与类别

【条款正文（v1.3 生效）】

- `pending-commit` / `orphan` 产物默认 TTL：**168 小时（7 天）**，类别 **A**（可先定，待实测校准），按环境可配置。
- TTL 从最后一次幂等关联尝试或最后一次引用检查时间起算。
- TTL 到期不等于可删除，只表示进入清理候选。

### 38.2 清理前置条件（全部满足才可清理）

1. 产物版本已固定，无进行中的写入。
2. 无任何 active / waiting / retrying / recovery 状态的 Task 引用。
3. 无 `evidenceRefs`、`sourceRefs`、审批记录、冲突记录或迁移记录引用。
4. 已通过至少一次引用扫描（含反向 lineage 检查）。
5. 清理动作已写入审计并可回溯。

### 38.3 审计例外（永不自动清理）

- 被任何已提交 Task 的 `artifactRefs` 引用。
- 与 R2/R3 动作、审批决定、外部副作用凭证相关。
- 参与 `ConflictRecord` 或作为裁决依据。
- 指向不可重建的外部证据（原始抓取、原始日志）。
- 处于审计保留期、调查、legal hold 或合规冻结。
- 被 `planVersion` 迁移记录、`rejected`/`failed` 终态记录引用。

【条款正文（v1.3 生效）】例外产物只能由人工批准清理；批准必须记录理由、批准人、时间与二次确认人（R3 相关）。

【建议，待用户确认】清理分两步：先标记 `orphan_expired` 并保留 tombstone 元数据（`artifactId`、哈希、引用扫描结果），再过二次保留期后才物理删除；二次保留期建议 30 天。

### 39.1 上限表

| 控制项 | 取值 | 类别 | 说明 |
| --- | --- | --- | --- |

| 检测时间上限 | 200 ms / 单次检测 | B | 待压测，未压测前不得作为生产标准 |

### 39.2 超限降级策略

【条款正文（v1.3 生效）】

1. 新增边前检测成环；超限时**拒绝新增边**（§17），不做“先加后修”。
2. 冻结受影响节点，不冻结整个 Run；其余无依赖节点继续推进。
3. 报告内容必须包含：图类型、当前节点数/边数/深度、超限维度、路径样本、`runId`、`traceId`。
4. 冻结导致无节点可推进时，才触发重规划；该次重规划计入 §36 的 Run 级 2 次上限。
5. 检测超时按“未完成检测”处理：拒绝新增边并冻结相关节点，**不得假设无环**。
6. 降级不得跳过安全校验、预算校验与权限校验（§13、§21）。

**关闭项：** 上一轮缺口 #16（§17 只有“设置上限”无具体值）。

### 40.2 防污染规则

【条款正文（v1.3 生效）】

- **隔离**：holdout 不向被优化 Agent 暴露样例与答案；访问受限、只读、留审计。
- **泄露检测**：样例指纹与近似重复检测；发现进入训练/提示词/上下文即判定泄漏。
- **单次消耗**：依据 holdout 结果调参即消耗，必须轮换，不得反复使用同一 holdout 调优。
- **去向记录**：记录 `datasetVersion`、来源、去重结果、泄漏风险、使用次数、使用人。
- **安全集独立**：隐藏安全案例、对抗样例、回归集单独保留，不进入日常迭代集。
- **防单一优化**：固定评测集不得成为唯一优化目标（§14）。
